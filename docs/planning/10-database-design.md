# 10 — Database Design

> Status: **Planned**. This is a design only: no schema has been created and no migrations have been run. · Owner: Database Architect · Conceptual model: [09](09-domain-model.md) · Decision: [ADR-0005](adr/ADR-0005-postgres-drizzle.md)

## 1. Conventions
- PostgreSQL 17. Each module gets its own schema: `identity`, `projects`, `integrations`, `requirements`, `testmgmt`, `execution`, `visual`, `defects`, `ai`, `codegen`, `automation`, `governance`, `analytics`, plus `pgboss` (owned by pg-boss) and `public` (extensions only).
- Primary key: `id uuid` (UUIDv7, generated by the application).
- Every project-owned table has `project_id uuid NOT NULL` and starts each composite index with `project_id`.
- Timestamps are `timestamptz`: `created_at` and `updated_at`. Mutable tables also have `created_by` and `updated_by` (user or service account ID).
- Optimistic concurrency: mutable aggregates have `version int NOT NULL DEFAULT 1`, and updates use `WHERE id = $1 AND version = $2`.
- Soft delete: `deleted_at`, only where the business needs it (projects, suites). Immutable records are never deleted, only purged by retention.
- JSONB is used for provider snapshots, typed settings sections (validated by Zod with a `schema_version`), and AI outputs. JSONB is never used for relational data that we query.
- Enums are Postgres `text` columns with `CHECK` constraints, which migrate more easily than native enums.
- Naming: snake_case, plural table names, and `fk_<table>_<col>`, `ix_<table>_<cols>`, `ux_<table>_<cols>` for constraints and indexes.

## 2. Roles and privileges
| DB role | Used by | Privileges |
|---|---|---|
| `qos_migrator` | `migrate` command only | DDL on all QualityOS schemas |
| `qos_app` | api, worker, controller | DML on module schemas; **INSERT/SELECT only** on `governance.audit_events`; no DDL |
| `qos_retention` | retention purge job | DELETE on purge-eligible tables (incl. expired audit partitions) |
| `qos_readonly` | analytics exports, support | SELECT on non-secret tables (no `governance.secrets`) |
| `n8n` | n8n container | Its **own database** `n8n`. No access to the QualityOS database |

## 4. Idempotency and duplicate-delivery constraints (summary)
| Concern | Constraint |
|---|---|
| Duplicate webhook delivery | `inbox_messages ux(connection_id, dedupe_key)` |
| Duplicate event dispatch to n8n | `workflow_dispatches ux(event_id, subscription_id)` + receiver dedupe on `event_id` via Automation API idempotency |
| Duplicate schedule firing | `automation_firings ux(rule_id, slot_key)` |
| Duplicate run creation | `run_requests ux(project_id, idempotency_key)` |
| Duplicate API mutation | `idempotency_keys pk(scope, key)` + request hash check (same key, different body → 422) |
| Duplicate result ingestion | `result_chunks pk(run_id, shard_index, seq)` |
| Duplicate external issue | Marker + `idempotency_keys(scope='defect.external.create', key=defect_id)` + `searchByMarker` |
| Duplicate notification | `notifications ux(user_id, dedupe_key)` |
| Duplicate document snapshot | `source_snapshots ux(source_id, checksum)` |

## 5. Immutability enforcement
- **Triggers:** `BEFORE UPDATE` triggers on `requirement_versions`, `test_case_versions` (after approval), `run_manifests`, `execution_attempts` and `step_results` (after the run is terminal), and `visual_baselines`. They raise an exception if protected columns change.
- **Terminal-run protection:** a trigger on `test_executions` and `execution_attempts` checks the parent run's state and blocks updates when it is terminal. Annotations go in `annotations`.
- **Audit:** enforced by DB privileges (§2).

## 6. Multi-project isolation
- Every repository method takes a `ProjectScope` and adds `project_id = $scope`. A lint rule plus a repository base class enforce this.
- Cross-project queries (dashboard) use an explicit `AccessibleProjects` scope (a list) and are reviewed.
- **Defence in depth (P11, OD-10):**
  - RLS policies on project-owned tables: `USING (project_id = ANY (current_setting('qos.project_ids')::uuid[]))`.
  - The setting is per transaction (`SET LOCAL`), set by the data-access layer.
  - System jobs use a `qos_system` role with `BYPASSRLS`, scoped to class-E jobs.
- **Future multi-org:** every root has `org_id`. Projects inherit it. RLS can add an org predicate.

## 7. Migrations
- Drizzle schema in each module's `infrastructure/schema.ts` → `drizzle-kit generate` → SQL in `packages/db/migrations/NNNN_name.sql` (reviewed).
- Hand-written SQL migrations for triggers, RLS, partitions, and extensions (`CREATE EXTENSION IF NOT EXISTS vector, pg_trgm, citext`).
- **Forward-only.** Destructive changes use expand → migrate data → contract across two releases.
- The `migrate` command runs in its own container step before app start in Compose (`depends_on: condition: service_completed_successfully`). The application never runs migrations itself.
- Seeds: `seed:demo` (demo project + mock connections + fixtures) and `seed:perf` (large synthetic dataset for performance tests).

## 9. Performance & partitioning
- **Partition candidates** (range by `created_at` month): `audit_events` (partitioned from day one), `execution_attempts`, `artifacts`, `ai_executions`, `inbox_messages`. Partition the rest when they exceed about 20M rows (NFR-SCAL-04). The Drizzle schema keeps PKs as `(id, created_at)` for partitioned tables.
- **Hot query indexes:**
  - run lists `(project_id, finished_at desc)`
  - results by binding `(automation_binding_id, created_at desc)` via executions
  - defects `(project_id, state)`
  - requirements coverage via `traceability_links ix(to_type, to_id, type, status)` and `ix(from_type, from_id, type, status)`
- **Connection budget (pilot):**
  - api pool 10
  - worker pool 10
  - controller pool 5
  - pg-boss internal pool 5
  - n8n has its own DB
  - Postgres `max_connections` 100

## 10. Backup & restore
- Nightly `pg_dump -Fc` of the QualityOS DB and the n8n DB, plus a tar of the localfs artifacts volume (or S3 replication in enterprise), plus the n8n export. All are encrypted with `age` to the admin's public key. Retain 7 daily, 4 weekly, and 3 monthly.
- **Enterprise:** WAL archiving (pgBackRest or the managed service's PITR) for RPO ≤ 15 min.
- The weekly `restore.verify` job restores into a scratch DB, then runs `scripts/verify-integrity.sql`:
  - row counts
  - FK checks
  - audit hash chain verification
  - a sample artifact checksum check

  Results go in `restore_verifications`.
